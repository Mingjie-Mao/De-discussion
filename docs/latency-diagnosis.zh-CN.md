# 2026-10-07 延迟定位

## 测量结果

目标为 Northflank 美国中部后端 + Neon 悉尼数据库，客户端位于悉尼。
同一个 HTTPS 连接交替发送匿名和 Member 请求，各接口各 5 次，全部成功。
这是小样本诊断，不是压力测试，也不能据此估算 p95/p99 或保证不会超时。

| 接口 | 匿名中位数 | Member 中位数 |
| --- | ---: | ---: |
| readiness | 215 ms | 675 ms |
| 帖子列表 | 633 ms | 1009 ms |
| 评论首屏 | 822 ms | 1183 ms |
| 当前账号资料 | — | 981 ms |

带 JWT 的每次请求都会重新校验数据库里的账号状态、角色和令牌版本，增加约 0.4 秒。
此校验保证封禁、降权和撤销及时生效，不能为了性能直接删除。
Android 公共帖子和评论读取已经不带 JWT；上表匿名列更接近实际公共读取路径。
之前带 Member JWT 的接口基准包含额外账号校验成本。

本轮连接池等待人数快照为 0，连接超时计数为 0；区间获取连接平均约 31 ms。
区间新增两条数据库连接，平均建立耗时约 1338 ms。
本轮 GC 新增一次 7 ms 暂停，没有发现与秒级卡顿对应的 GC 停顿。
这些结果只说明本轮未观察到连接池饥饿或长 GC，不能排除历史问题。
CPU 指标的归一化方式与 0.2 vCPU 配额不同，不能把指标 0.159 直接解释为配额使用率 15.9%。

此前后端到悉尼数据库的 SELECT 1 单次往返约 189–191 ms。
新建连接、账号验证和事务中的多次串行往返会累计这段跨区成本；
这比“数据只有几条，所以应该很快”更能解释当前正常请求的延迟。

## 客户端检查

- 点赞已有乐观更新：先反馈，失败时回滚；真实保存仍需要服务器确认。
- 已加载评论的折叠/展开是本地操作，不会每次请求评论接口；首次加载、过期刷新和翻页需要网络。
- 评论缓存有效期 15 秒。翻译已采用后台执行、结果缓存及有界轮询，避免让页面等待模型完成。
- 后台社交状态读取已与写入拆分执行器，慢状态读取不会阻挡点赞写入；隔离设备测试验证了排队与旧响应覆盖的防护。历史卡顿中此因素的占比仍不确定。

## 尚未确认的偶发慢请求

旧设备日志中有 GET 5364 ms 和 POST 4820 ms。
后者对应服务器 refresh 日志约 4429 ms，说明那次大部分耗时位于服务器处理路径。
前者未找到对应服务器慢日志，不能据此确认是网络或数据库故障。
空闲 6 分钟后曾测得 profile 3422 ms、服务器同请求 3224 ms；没有同时记录 Neon 状态，不能断言是数据库休眠。
仍需在发生时关联客户端请求、服务器日志、连接创建和平台资源数据。

## 优先处理顺序

1. 让后端与数据库处于同一地区，减小每次 SQL/连接建立的网络成本。
   保持现有数据时可迁移后端到数据库附近；移动数据库则需要完整复制与切换验证。
2. 复用同一个请求已经验证的账号信息，避免 profile 重复查询；本人帖子使用专用分页查询，避免串行扫描多个论坛。
3. 读页面先展示已有缓存，再刷新。删除、隐藏、封禁后及时失效；不要用长期权限缓存换性能。
4. 对慢请求记录安全的路由模板、客户端排队/请求耗时和请求 ID，测量 p50/p95/p99。
5. 仅对适合重试的调用执行有限重试和退避；新增写入必须有幂等机制。重试提高成功率，不消除普通请求延迟。

## 本轮代码优化（已部署并完成线上验收）

- 账号校验使用新鲜的单语句查询，`/api/users/me` 复用本次校验的不可变资料。
  资料读取从 2 条 SQL/2 个显式事务变成 1 条 SQL/0 个显式事务。
  每次请求仍重新查询，不缓存封禁、权限或令牌撤销状态。
- 帖子列表和作者列表的数据、作者及媒体在同一 SELECT 中获取，减少显式事务往返。
  匿名列表保持 1 条 SQL，显式事务从 1 个变为 0 个；PostgreSQL 语句本身仍具有原子性。
- 新增作者分页接口和 V18 部分索引。个人主页从依次扫描多个论坛改成一次有界请求，
  使用时间和 ID 游标；相同时间不会重复或漏项，隐藏/删除内容不返回。
- 后台社交状态读取和写入分用执行器。点赞不再排在状态读取后面；
  版本检查拒绝写入前/写入中发起的旧状态响应，避免覆盖已经确认的点赞。
- 慢请求日志增加固定路由模板，去除 UUID 和查询串；社交队列另记超过一秒的排队时间。
  用于区分后续延迟是排队还是 HTTP，日志不记录令牌和内容。
